## Original detailed findings

### F01 — P0: database API permits cross-tenant child records

Evidence: core schema `campaign_locations` and `rewards` definitions and policies, plus `20260902090000_lock_remaining_client_writes.sql`.

The child rows carry independent org_id and campaign_id. Their write policies authorize the child org_id, while the foreign key validates only that the campaign exists. No composite ownership constraint or corresponding parent-ownership policy was found. Authenticated catalog INSERT/UPDATE remains granted. An org-A user can therefore submit a child with org-A ownership and a live org-B campaign identifier through the database API. The location RPC checks the parent, but direct table writes bypass that RPC. Privileged verification and reward selection query by campaign_id, so a foreign pin can become a valid verification location and a foreign reward can enter selection.

Fix: enforce `(campaign_id, org_id)` against the campaign's ownership in database constraints and policies; remove unnecessary direct writes. Test cross-org insert and reassignment for all child tables under real authenticated roles. Validate on staging before testing production.

### F02 — P1: brand deposits cannot persist their payment intent

Evidence: `lib/actions/finance.ts`, initiateBrandDeposit; `20260902090000_lock_remaining_client_writes.sql`, payment_intents revocations; commercial-engine SELECT-only intent policy.

The action initializes a payment then inserts payment_intents using the signed-in user's client. The migration explicitly revokes authenticated INSERT. With the repository grants applied, deposit creation fails after provider initialization. The checkout URL is withheld, breaking the revenue path.

Fix: authenticated, ownership-checked server/RPC intent creation with narrowly scoped privileges. Persist a durable reference before external initialization; preserve safe retries and orphan recovery. Do not reopen unrestricted client writes to money tables.

### F03 — P1: successful payment can remain permanently uncredited

Evidence: `app/api/payments/webhook/route.ts`, success branch; same ordering in sandbox completion.

Intent status is set to succeeded before credit_org_deposit runs. If credit fails, the route returns 500; a provider retry sees succeeded and returns without crediting. Status and money have diverged permanently. Several Supabase update/query errors are also ignored.

Fix: atomically settle intent + ledger + account, using a provider-verified transaction. Retry based on the durable ledger result. Inject a credit failure, resend concurrently and confirm exactly one credit and recoverable status.

### F04 — P1: test and live money share balances; webhook accepts unsigned sandbox payloads

Evidence: payment provider factory, sandbox provider, webhook route and credit_org_deposit.

The factory defaults to sandbox. Sandbox verifyWebhook accepts parsed JSON without a signature, and the webhook endpoint still calls the privileged credit RPC. Test credits use the same org account, campaign budget and creator wallets as live credits; is_sandbox is intent metadata, not a balance boundary. A forged webhook matching a pending intent can credit it when sandbox is selected. Production switching does not isolate or remove existing test liabilities.

Fix: explicitly fail closed for live deployments with missing configuration, disable sandbox endpoints there, use separate databases/accounts for testing, and reconcile existing test balances before enabling live funds. This risk is conditional on provider configuration and reachable matching intents.

### F05 — P1: webhook settlement lacks transaction matching and reliable lifecycle recovery

Evidence: webhook processWebhookEvent and `lib/payments/paystack.ts`.

The handler looks up reference only and credits the stored amount without checking received amount, currency, provider or test/live domain. Unknown references are logged then acknowledged as processed, losing automatic recovery if the intent is created later. Event deduplication uses transaction id/reference rather than event type + resource, which can suppress later lifecycle notifications. Refund/dispute ledger handling is absent. A fresh failure event can also downgrade an already succeeded intent without reversing its credit.

Fix: validate all settlement fields against a durable intent, keep unmatched events retryable, define legal state transitions and event identity, and implement audited refunds/disputes and reconciliation jobs.

### F06 — P1: webhook signing configuration does not match all supported Paystack modes

Evidence: route reads x-paystack-signature and HMACs using PAYSTACK_WEBHOOK_SECRET/PAYMENT_WEBHOOK_SECRET. It does not read Paystack-Signature.

Current Paystack docs describe timestamped Paystack-Signature signing and legacy x-paystack-signature using the API secret key. The route has neither the new verifier nor an explicit legacy API-key verifier. A separately configured secret may reject every legacy real payment; accounts migrated to the new header cannot be handled correctly.

Fix: implement and test the configured provider's documented signature scheme, timestamp tolerance, rotation and malformed-header handling. See [Paystack webhook documentation](https://paystack.com/docs/payments/webhooks/).

### F07 — P1: rewards are issued after stock is exhausted

Evidence: latest unlock_campaign in `20260902120002_visit_risk_score_unlock_hook.sql`.

The function inserts the reward claim first, then conditionally increments redeemed_count only when stock remains. A zero-row update is ignored, so stock=0 still produces a claim. Concurrent users can also exceed inventory. The displayed redeemed_count tracks issuance, rather than actual redemption.

Fix: atomically reserve inventory before issuing the claim; reject or return an explicit out-of-stock result and keep counters semantically distinct. Test the last unit with concurrent distinct consumers.

### F08 — P1: platform fees are reported but remain spendable by campaigns

Evidence: latest fund_campaign_budget; debit_campaign_budget_for_verified_visit; getPlatformRevenueSummary.

Funding reserves the whole gross budget and records a positive platform_fee, but leaves campaign spent/reserved at zero. Visit billing uses gross total minus spent minus reserved, not the post-fee balance or performance allocation. A R1,000 campaign with a R150 fee can consume all R1,000 in visits while the dashboard still reports R150 revenue. Allocations are checked only at creation, not enforced per spending category.

Fix: define a balanced accounting model separating platform revenue, campaign service budget and liabilities. Enforce net and category limits in each debit. Reconcile org reserves, campaign balances, earnings, provider cash and revenue with real database tests.

### F09 — P1: closing campaigns does not return unused brand funds

Evidence: campaign lifecycle action only changes campaign status; latest funding RPC rejects every existing budget; no budget release/refund action found. Funding migration itself documents stranded reserves.

An ended/archived campaign can leave money locked in org reserves with no supported release or refund path. Customers cannot top up the same existing budget through the funding action.

Fix: implement audited close/release and separately defined top-up/refund operations with idempotency, permissions, outstanding liability checks and reconciliation.

### F10 — P1: verification trusts caller-supplied GPS and races under parallel check-ins

Evidence: latest record_interaction_event and verify_location_checkin.

Coordinates and accuracy originate from the caller; missing accuracy passes. The ten-minute check is a count followed by updates without a per-user/campaign lock or unique billing interval. Two different pending events verified concurrently can both pass and each cause visit spend. Risk scoring runs after verification and billing and does not block suspicious earnings. No-pin events can become verified location check-ins.

Fix: serialize verification and billable visit entitlement, bound and require valid input, distinguish unverified location assertions from merchant-backed proof, and place suspicious payments/earnings under review before release. Browser GPS alone is not proof against a modified client.

### F11 — P1: campaign schedule and required mechanics are not enforced by unlock

Evidence: latest unlock_campaign checks status=live and presence of a recent visit when pins exist. It does not enforce starts_at, ends_at or experience_configs.verification_required. Public map RPC also filters status only.

A live future/expired campaign remains accessible and unlockable. QR/NFC/product/quiz requirements configured by a brand are not authorization conditions in this RPC. The general unlock path can issue the same reward used by product-code claims, bypassing that separate flow's purpose.

Fix: centralize server-side eligibility for schedule, campaign state and actual authoritative mechanic evidence. Ensure UI promises match the selected mechanic. Test direct RPC calls without completing the expected steps.

### F12 — P1: production dependencies require a security upgrade

Evidence: package.json and lockfile pin Next 14.2.35. Vendor's May 2026 release identifies all Next 14 versions as affected by that coordinated security release.

Fix: move to a currently supported, patched release and verify applicable advisories, framework changes and deployment checks. Do not assume a successful old deployment establishes security. No claim is made that every listed advisory is exploitable in this app. See [Vercel security release](https://vercel.com/changelog/next-js-may-2026-security-release). Full npm advisory inventory could not complete in this environment.

### F13 — P1: fresh installs and database rebuilds are not reproducible

Evidence: npm ci failure; `00000013_unlock_creator_earning_bridge.sql` ends by granting EXECUTE on unlock_campaign(uuid), although it dropped that overload and defined only the two-argument function. A default argument does not create a shorter function signature. Two migration files also share version 00000013.

The invalid grant prevents a strict clean replay from reaching later repairs. Duplicate versions require reconciliation with actual migration history before CLI-based rebuilds. Older certification instructions stop before later mandatory fixes.

Fix: reconcile historical migrations safely against production, supply a proven clean bootstrap, regenerate the lockfile, and run CI from an empty database and clean checkout. Do not blindly rename or reapply already deployed migration versions.

### F14 — P1: payout execution is incomplete

Evidence: getPayoutProvider is a sandbox stub with simulated paid status; no invocation of a live payout provider was found. Admin completion records paid without provider verification and accepts optional references.

The app can record a payout without transferring money. Manual payout operations need an explicit verified process, recipient details, receipt and reconciliation; the application is not an automated bank payout system.

Fix: implement verified recipient onboarding and payout initiation/status/webhooks, or ship a clearly documented manual process with mandatory evidence and separate approval/completion states.

### F15 — P1: redemption records a consumer click, not merchant fulfilment

Evidence: redeem_reward_claim only authenticates claim ownership and changes claimed to redeemed. It does not verify merchant approval, a voucher/one-time token, expiry or fulfilment. RedeemButton then requests REWARD_REDEEM through recordInteraction, which explicitly rejects that event type, and ignores the result.

Fix: define redemption semantics, expiry and merchant verification. Record authoritative redemption analytics in the transaction, and ensure no customer loses a voucher by pressing a button before the merchant honours it.

### F16 — P2: tests do not prove concurrency, tenant isolation or reconciliation

Evidence: test-unlock-concurrency's extractUnlockBody uses lastIndexOf("function public.unlock_campaign("), which matches the later GRANT line rather than the CREATE body. Eight assertions therefore fail from extraction, not eight demonstrated runtime defects. Its 'concurrent' scenario is a sequential loop over JavaScript Sets. Finance/fraud/reconciliation scripts reproduce their own simplified rules. Tenant isolation script explicitly passes some skipped fixture checks.

Fix: repair SQL extraction, then add actual Postgres role, last-stock, budget, check-in and settlement concurrency tests. Require two populated tenants, consumers and creator accounts. Missing fixtures must not qualify as production proof.

### F17 — P2: moderators' hides can be reversed by content owners

Evidence: experience_social UPDATE policies authorize own rows and allow column-wide updates. Admin moderation sets the same deleted_at/hidden_at fields those users can update.

An owner can clear a moderation hide or reassign a post to another campaign while remaining its owner. Inserts do not require a live/eligible campaign. Follow-notification triggers fan out for every post/comment without product-specific rate limits.

Fix: separate user deletion from admin moderation, restrict mutable columns and campaign eligibility, and bound posting, media uploads and notification fan-out. Verify direct SDK writes, not just the UI.

### F18 — P2: legal and support pages are visibly unfinished

Evidence: terms/privacy pages label themselves baseline drafts. Privacy text omits precise GPS evidence, public social/media behavior, concrete retention periods and a usable deletion contact. Product code stores location in event/verification JSON. Brand event drilldown includes user IDs and risk reasons.

Fix: map actual data processing and public visibility, add working contact/deletion/support routes, and obtain appropriate review of paid campaign, reward, refund and creator terms. This finding is about missing product disclosures and operating processes, not a legal compliance certification.

### F19 — P2: database failures are presented as empty/zero business data

Evidence: getBrandFinancials/getCreatorWallet ignore individual query errors and substitute empty lists/zero wallet; getPlatformRevenueSummary ignores ledger errors and fetches unpaginated rows. Several aggregate pages similarly sum unpaginated results.

Missing permissions/migrations can look like no transactions. API row limits can undercount platform revenue as volume grows. The platform summary omits provider charges and running costs, so its net revenue figure is not business profit.

Fix: distinguish unavailable from zero, paginate or aggregate in authorized SQL, add settlement reconciliation and operational alerts, and label financial measures accurately.

### F20 — P2: repeat-audience notification feature is disconnected and uses the wrong column

Evidence: notifyBrandWalkers selects interaction_events.consumer_id, while the schema uses user_id. No caller of notifyBrandWalkers was found. The helper also suppresses query failures as no history.

Fix: connect an authorized publish job to campaign-scoped verified user_id history, with consent and delivery limits, or remove claims that this retention feature is active.

## Commercial assessment

The narrowest saleable product is a funded, limited-location store-visit campaign with a real merchant reward and an auditable outcome report. Sell that only once its money and fulfilment path passes. Current interface concepts for purchases, QR/NFC and wider engagement exceed what the central verifier enforces.

Before setting a price, agree what a billable unique visit means, who pays for rewards, whether creator compensation is included in visit cost, what happens on suspicious activity, when the platform fee is earned and when unused balances return. A default 15% fee and R20 visit rate in code do not demonstrate margin. Measure collected fees less provider charges, creator payments not already included in cost, support, fraud/refunds, fulfilment and infrastructure per pilot. Use real signed merchant commitments and measured results; no revenue forecast is justified by this source audit.

## Fix order and release acceptance

1. Close tenant contamination and production test-money boundaries; move to supported dependencies. Restore reproducible installs and migration replay.
2. Repair durable intent creation and atomic, verified settlement. Exercise invalid signature, wrong amount/currency/provider, early webhook, lost response, failure after credit, duplicate/concurrent delivery, refund and dispute.
3. Establish balanced fee, spend, creator and refund accounting. Test exhausted budgets and close/release; reconcile to provider cash.
4. Enforce schedule/mechanics, atomic reward stock, billable visit uniqueness, reviewed earnings and merchant redemption.
5. Complete payout operations, error visibility, legal/support disclosures and monitoring.
6. Run a staging end-to-end pilot with separate brand, consumer, creator and admin accounts. Then verify the intended production project and deploy commit, live configuration, email delivery, backups, logs and database advisors.
7. Execute a controlled, explicitly authorized real-money acceptance transaction with its refund and payout proof. Finish mobile/iOS/Android, accessibility, map/network failure and load checks before public launch.

Release evidence must include clean install/build/lint, fully populated cross-tenant tests, database concurrency results, provider settlement records, ledger reconciliation, merchant fulfilment proof and a rollback/recovery runbook. Until then, source fixes or HTTP 200 responses cannot certify readiness to accept customer money.
